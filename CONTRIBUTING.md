# Contributing to kat

Issues and pull requests are welcome.

## Reporting bugs and asking for features

Open a [GitHub issue](https://github.com/zemanlx/kat/issues) and use the bug report or the feature request form.
For a bug, include:

- the kat version (`kat -version`), and the `-k8s-version` you passed, if you passed one
- the policy, the binding and the test files involved, with a minimal object that shows the problem
- the command you ran, what you expected and what happened; the output of `kat -v <dir>` usually shows why

Issues are public. Remove Secret data, credentials and anything else sensitive before you post.

Report security vulnerabilities privately as [SECURITY.md](SECURITY.md) describes, not in an issue.

## Proposing a change

1. For anything bigger than a small fix, open an issue first so we can agree on the approach.
2. Branch from `main` and open a pull request against `main`.
3. Write commit messages and the pull request title as [Conventional Commits](https://www.conventionalcommits.org/):
   `feat:`, `fix:`, `docs:`, `test:`, `ci:`, `chore:`, with `!` for a breaking change.
4. Sign your commits. The `main` branch only accepts signed commits.
5. CI must pass: `go test -v ./...`, golangci-lint in the root and in `conformance/`, and the conformance
   matrix against a real kube-apiserver for every version in `conformance/k8s-versions.json`.

## Development

You need the Go version in `go.mod`. kat is built and tested offline, so no cluster is needed.
The conformance tests also need bash 4 or later. macOS ships bash 3.2, so install a newer one.

```bash
go build ./...                          # build everything
go test ./...                           # run all Go tests
go test -v ./...                        # what CI runs
go test -update ./...                   # regenerate golden files (testdata/*.golden), then review the diff
golangci-lint run                       # lint the root module (golangci-lint v2)
(cd conformance && golangci-lint run)   # lint the conformance module
./hack/conformance.sh                   # conformance tests for every version in conformance/k8s-versions.json
./hack/conformance.sh 1.37.x            # conformance tests for one version
```

`hack/conformance.sh` downloads kube-apiserver and etcd into `bin/envtest`. Do not commit the built `kat`
binary; it is gitignored.

kat takes directories, not single files. To run one case, pass its policy directory and use `-run`:

```bash
go build -o kat . && ./kat -v -run "without-label" ./test-policies-pass/validating/require-owner-label
```

## Tests

- New behaviour comes with tests that cover it.
- A bug fix starts with a test that fails without the fix.
- New or changed admission behaviour gets a case under `test-policies-pass/`. The conformance suite compares
  every case there with a real API server. Deny cases belong there too.
- `test-policies-fail/` holds cases that check how kat reports failures. Every case in it is expected to fail,
  so do not put admission cases there.
- Write test cases with the [write-kat-tests skill](skills/write-kat-tests/SKILL.md). It has the filename
  grammar and copy-ready templates.
- When kat and the API server differ, and the fix is not a small change to kat, add an entry to
  [`conformance/known-divergences.yaml`](conformance/known-divergences.yaml). Give the suite, the case, the
  Kubernetes versions it applies to, the reason, and a tracking issue if there is one. A listed case must
  still fail. Once kat matches the server, the test fails with "unexpected pass" until the entry is removed.

## Code style

- `golangci-lint run` must be clean in the root and in `conformance/`, with the repository's
  [.golangci.yaml](.golangci.yaml). `golangci-lint fmt` applies the formatters that the config enables.
- The `evaluator` package is public. kar imports it, and `CompileValidating` audits existing objects,
  so keep its API stable.
- Comments explain constraints the code cannot show, not what the next line does.
- `internal/ssa/swagger.json` is generated by `./hack/update-schema.sh`. Do not edit it by hand. Run the script
  after you bump the `k8s.io/*` modules. The drift guard in `internal/ssa/ssa_test.go` checks that the schema
  matches them.
- Keep changes minimal and scoped to the task. Match the existing code and comment style.
- When behaviour changes, update [README.md](README.md) in the same pull request.
- Workflow changes keep actions pinned by commit SHA and permissions minimal; see the "CI and supply chain"
  section of [AGENTS.md](AGENTS.md).
